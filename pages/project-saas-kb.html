Knowledge Base · Kovai.co

How a Structured Knowledge Base Cut Support Tickets in Half

When I joined Kovai.co, users raised support tickets for issues that documentation should have resolved. I built the knowledge base from scratch — mapping real ticket patterns, filling the highest-impact gaps, and establishing a release-cycle publishing workflow. Within two quarters, support ticket volume dropped by 50%.

The Problem

No Documentation. All Tickets.

When I joined Kovai.co as a Technical Writer, the product had no structured knowledge base. Every user question — regardless of how common or simple — landed in the support queue. The customer support team was spending the majority of their time answering the same issues repeatedly, and users experienced delays that damaged product trust.

The root cause was clear: there was no self-serve resource where users could find answers independently. The product was growing, the user base was expanding, and without documentation, the support load would only compound. My brief was to fix that — from zero.

My Role

End-to-End Ownership

I was the sole owner of this project across every stage — there was no existing documentation team, no templates to inherit, and no editor to review my work. I was responsible for:

  • Analysing the support ticket backlog to identify documentation gaps
  • Interviewing subject matter experts (engineers and PMs) to gather accurate technical content
  • Designing the information architecture and category structure
  • Writing, editing, and publishing all articles in Document360
  • Coordinating with the support team to validate coverage
  • Establishing a release-cycle publishing workflow for ongoing updates
  • Tracking article performance and iterating based on search data

Process

How I Built It

01

Ticket Audit

I pulled 3 months of support tickets with the customer support lead and grouped them by topic. This gave me a data-backed priority list — the 20 categories accounting for 80% of ticket volume became my first writing targets.

02

Information Architecture

I mapped a category structure in Confluence before writing a single article — product areas, task types, and user journey stages. The goal was a structure users could navigate without a search bar.

03

SME Interviews (Async)

I drafted articles first using product access and existing notes, then sent targeted questions to engineers via Confluence comments — never meeting-first. This kept the process lightweight enough that busy devs actually responded.

04

Draft, Review, Publish

High-priority articles were drafted, reviewed by the support team for accuracy, and published in Document360 with screenshots from Snagit. I shipped the first 20 articles within 6 weeks.

05

Ongoing Release Cycle

I embedded myself in the sprint cycle — attending sprint reviews to flag documentation-impacting changes and updating articles on the same day features shipped. Documentation was never behind the product.

Challenges & Solutions

What Stood in the Way

Challenge Engineers unavailable for reviews
The engineering team was in an active sprint cycle and had no time for documentation meetings or synchronous review sessions.
Solution Async review via Confluence comments
I switched to async reviews entirely — drafting articles with specific inline questions for engineers to answer in their own time. Response rates improved immediately because the effort per review dropped to under 5 minutes.
Challenge No existing content baseline
Starting from zero meant every article had to be researched, written, and validated without any existing docs to build on or reference.
Solution Ticket-first prioritisation
Rather than trying to document everything at once, I used the ticket audit to identify the 20 highest-impact topics. Shipping these first meant the KB had measurable impact within weeks — long before the full library was complete.
Challenge Keeping docs in sync with fast releases
The product shipped updates frequently, and documentation could become outdated within days if there was no process to catch changes.
Solution Sprint-embedded documentation workflow
I joined sprint review calls and added documentation tasks directly to Jira alongside dev tickets. Any feature that shipped without a documentation update was flagged as incomplete. This made docs part of the definition of done.

Takeaway

What This Project Taught Me

Documentation is most valuable when it is built backwards from user pain — not forwards from product features. Starting with the ticket audit rather than the product spec meant every article I wrote had an immediate, real use.

It also reinforced that documentation velocity depends on process design as much as writing skill. The async review system and the sprint-embedded workflow were not documentation decisions — they were collaboration decisions. Getting those right is what made the rest of it possible.
